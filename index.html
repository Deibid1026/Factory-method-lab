¿Qué es Factory Method?

Define una interfaz para crear un objeto, pero deja que las subclases decidan qué clase instanciar. Factory Method le permite a una clase diferir la instanciación a sus subclases.

También se conoce como Constructor Virtual.

Problema que resuelve: Cuando una clase de alto nivel necesita crear objetos, pero no puede anticipar la clase concreta que debe instanciar. Usar new ClaseConcreta() directamente acopla el código y viola el Principio Abierto/Cerrado.
Motivación clásica (GoF)

Un framework de aplicaciones tiene dos clases abstractas: Application y Document. Application sabe cuándo crear un Document (al hacer "Nuevo"), pero NO sabe qué tipo crear — eso depende de la aplicación concreta.

La solución: Application declara un método abstracto createDocument(), y cada subclase (DrawingApp, SpreadsheetApp) lo implementa devolviendo el tipo correcto.

¿Cuándo usarlo?
  • Una clase no puede prever la clase de los objetos que debe crear.
  • Se quiere que las subclases especifiquen los objetos que se crean.
  • Se busca desacoplar el código cliente de las clases concretas.
  • Se trabaja con frameworks extensibles donde otros desarrolladores definen los productos.

Consecuencias

✓ Ventajas

  • Bajo acoplamiento entre creador y producto
  • Cumple el Principio Abierto/Cerrado
  • Responsabilidad única (lógica de creación separada)
  • Facilita extensión sin modificar código existente

✗ Desventajas

  • Más subclases (puede ser sobre-ingeniería)
  • Todos los productos necesitan una interfaz común
  • El cliente debe elegir qué ConcreteCreator instanciar
Estructura formal del patrón

Diagrama de clases (UML)

Los cuatro participantes y sus relaciones:

Participantes
RolDescripción
ProductInterfaz que deben cumplir todos los objetos creados por el factory method.
ConcreteProductImplementación específica de Product.
CreatorDeclara el factory method (puede tener implementación por defecto) y lo usa internamente — nunca crea productos directamente.
ConcreteCreatorSobrescribe el factory method y decide qué ConcreteProduct instanciar.
Ejemplo de código
// Product
interface Notificacion {
  enviar(String msg, String dest);
}

// Creator (abstracto)
abstract class ServicioNotificacion {
  abstract Notificacion crearNotificacion();  // factory method

  void notificar(String msg, String dest) {
    Notificacion n = crearNotificacion();      // vía la interfaz
    n.enviar(msg, dest);
  }
}

// ConcreteCreator
class ServicioEmail extends ServicioNotificacion {
  Notificacion crearNotificacion() {
    return new NotificacionEmail();  // ← única decisión concreta
  }
}

Enunciado

Una empresa de logística necesita exportar su lista de envíos en distintos formatos. Debes aplicar el patrón Factory Method para que el sistema pueda generar un ReporteEnvios en tres formatos: PDF, Excel y CSV.

Requisitos:

  1. Define una interfaz ReporteEnvios con el método generar().
  2. Implementa tres clases concretas: ReportePDF, ReporteExcel y ReporteCSV.
  3. Crea una clase abstracta FabricaReporte con el factory method crearReporte() (abstracto) y un método generarReporte() que use el factory method internamente.
  4. Implementa las tres fábricas concretas correspondientes.
Tu código (Java, Python o pseudocódigo)
Solución de referencia
// 1. Product
interface ReporteEnvios {
  void generar();
}

// 2. ConcreteProducts
class ReportePDF implements ReporteEnvios {
  public void generar() {
    System.out.println("Generando reporte PDF de envíos...");
  }
}
class ReporteExcel implements ReporteEnvios {
  public void generar() {
    System.out.println("Generando hoja Excel de envíos...");
  }
}
class ReporteCSV implements ReporteEnvios {
  public void generar() {
    System.out.println("Exportando CSV de envíos...");
  }
}

// 3. Creator (abstracto)
abstract class FabricaReporte {
  abstract ReporteEnvios crearReporte();  // factory method

  void generarReporte() {
    ReporteEnvios r = crearReporte();
    r.generar();
  }
}

// 4. ConcreteCreators
class FabricaPDF extends FabricaReporte {
  ReporteEnvios crearReporte() { return new ReportePDF(); }
}
class FabricaExcel extends FabricaReporte {
  ReporteEnvios crearReporte() { return new ReporteExcel(); }
}
class FabricaCSV extends FabricaReporte {
  ReporteEnvios crearReporte() { return new ReporteCSV(); }
}

// Uso en el cliente:
FabricaReporte f = new FabricaPDF();
f.generarReporte();  // Cliente no conoce ReportePDF

Lo que aprendiste hoy
  • Intención: diferir la instanciación a subclases para desacoplar el creador del producto.
  • Cuándo usarlo: variedad real de productos que puede crecer, framework extensible.
  • 4 participantes: Product, ConcreteProduct, Creator, ConcreteCreator.
  • Clave: Creator solo conoce la interfaz Product; nunca la clase concreta.
  • Costo real: más subclases — no aplicar cuando hay solo 1 o 2 tipos fijos.
